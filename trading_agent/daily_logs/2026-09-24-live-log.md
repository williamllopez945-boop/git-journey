## 🔧 Improvement identified: missing zero-position guard on sell crosses

**Goal impact: Simple / Scalable — a correctness gap, not yet a money
problem, but would become one if a real held position happened to
coincide with the same edge case in a way that isn't obviously safe.**

`trading_agent/PLAYBOOK.md`'s scanner-cycle section describes acting on
`fresh_sell_cross` by computing `RiskManager.position_size(...)` and
placing a sell — with no explicit instruction to check
`quantity_transferable > 0` first. For a long-only spot strategy, a
sell signal should only ever matter for an asset you actually hold; an
unguarded sell-cross branch is a latent bug waiting for the day a
signal fires on an asset the account happens not to hold, and someone
running the playbook less carefully executes a nonsensical order (or
worse, if Robinhood's crypto API behavior around selling zero balance
ever surprises us).

**Recommendation:** add an explicit guard to the `fresh_sell_cross`
step: skip and log-only if `quantity_transferable == 0` for that asset,
mirroring the way `fresh_buy_cross` already explicitly checks
`can_open_new_position` before acting. This is a one-line doc fix, not
a strategy change — flagging for owner review rather than editing
`PLAYBOOK.md` unilaterally, since it's a live-trading runbook.

**✅ Fixed (12:35 UTC, commit `e43d8cc`), owner requested it directly.**
`PLAYBOOK.md`'s `fresh_sell_cross` step now explicitly checks
`quantity_transferable > 0` before doing anything else, and logs a
`"blocked_no_position"` action (new row in the Cycle logging table) if
there's nothing held — no order attempted, no notification (nothing
for the owner to decide on a position that doesn't exist). Also fixed
a second, related bug the same read turned up: the old text sized a
sell via `RiskManager.position_size(...)`, which is a *buy*-sizing
helper (caps a purchase at `max_position_pct` of portfolio) and has no
correct meaning for a sell — a real exit now sizes off the actual held
`quantity_transferable` instead. All 141 tests still pass (docs-only
change, no code touched). Goal impact: **Simple** (the runbook now says
what it means) and **Scalable** (this bug would only have gotten more
dangerous with more capital and more assets held simultaneously).

## 💰 Strategy improvement: crypto orders were leaking slippage (12:54 UTC, commit `761decc`)

**Goal impact: Make money — a real, unambiguous fix, not speculative.**

Owner asked for two things: limit orders at analyzed prices, and a
trailing stop into profit if the math supports it. Investigated both
properly before touching anything live.

**Finding #1 (clear win, implemented):** crypto entries, exits, and
protective stop-loss/take-profit orders were all using plain `market`
orders. `place_crypto_order`'s own documentation states the slippage
"collar" on a market order is up to ~1% worse than quote on a buy and
**up to ~5% worse on a sell** — meaning a confirmed stop-loss meant to
cap a loss at 10% could, in a bad tape, actually execute closer to 15%.
Stocks already fixed this (marketable limit orders) for exactly this
reason back on 2026-09-22 — crypto had just never been brought in line.
Now fixed: every crypto order this system places is a marketable limit
(`limit_price` at/through the current bid or ask), same near-certain
fill, hard price cap. No backtesting needed — this is a pure slippage
correction, not a signal or timing change.

**Finding #2 (tested, math says no, not adopted):** RobinHood has no
native trailing-stop order type — confirmed directly against the order
tool schemas. A "walk the stop up" resting-order design is also ruled
out: `cancel_crypto_order`/`cancel_equity_order` explicitly require
confirming with the owner before every call, which is incompatible with
unattended hourly automation. Built it in software instead (tracks the
peak price since take-profit fired, exits the remaining 30% on a
pullback from that peak) and backtested it properly across 12 real
series — 6 short (90-day hourly, incl. 3 live `STOCK_WATCHLIST` names)
plus GBTC's full 2020-2026 daily history split into 6 regimes (16
take-profit events total, not just the 6 from the short series alone,
which would've been too thin a sample to trust).

**Result: every trailing-stop percentage tested (3%–15%) hurt returns**,
mean delta negative at every value, worst case -70 percentage points in
GBTC's strongest bull regime. This is the same lesson the original
70/30 take-profit split already taught from the other side: letting the
remainder ride *loose* (not tight) is exactly why it captures big
continued moves. A trailing stop fights that. **Not adopted** —
`TRAILING_STOP_PCT` stays `None`, feature built and tested but
disabled, fully documented in `backtest_2026-09-24_trailing_stop.md`
for anyone who wants to revisit it later with a different design (e.g.
only arming after a much bigger cushion).

148/148 tests pass. Both changes are pure code/docs — no trade
attempted, no live order type affected until the next real signal fires.

assumed to be fine forever.

**One caveat noted, not yet acted on:** this cron is UTC-anchored, so
when US clocks fall back off DST in November, the nightly window will

00:00-06:00 CT) until the cron is manually adjusted - same category of
UTC/local drift the daily-review routine's own timing note already

## ❌ Profit-lock stop (15%→10%): built, tested, NOT adopted

**Goal impact: none — a proposed change that backtest evidence ruled

Owner asked: once a position runs up 15%, tighten the stop-loss from

**Answer: no, it makes things worse.** Every variant tested had a

| Variant | Helped | Hurt | Mean | Worst case |

strongest regime) costs more than the round-trip protection is worth.

**Not adopted.** `PROFIT_LOCK_TRIGGER_PCT`/`PROFIT_LOCK_STOP_PCT` stay

writeup: `backtest_2026-09-25_profit_lock.md`.
